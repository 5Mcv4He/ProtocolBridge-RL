# 从设备语义到可求解的寄存器任务

一个协议验证组件可以检查请求有没有遵守总线规则，却不能自行决定设备应该怎样更新状态。例如，同样是“向某位写入 1”，普通读写寄存器应保存它，W1C 状态位应清除它，只读寄存器应保持不变。把这些不同含义写进契约，并独立检查实际状态，是让工业工具成为任务评分后端的关键一步。

本阶段将[有限 APB 寄存器族](../task_families/apb_register_v1/README.md)接入原生 Agent 运行闭环。**两份设备契约完成分层准入，一份预先选定契约完成一条真实求解、独立评分及轨迹审计。** 这验证了新工程域可以沿用现有交互机制；它没有证明模型具有稳定的寄存器设计成功率。

## 哪些能力复用，哪些必须重新验证

已有 X2P 工作解决了求解接口的一部分问题：模型通过原生工具调用读取规格、编辑一个文件、运行公开测试，最后提交并停止。原生调用的参数检查、预算、反馈送达与临时工作目录没有因接口从 AXI/APB 桥变成 APB 从设备而改变。

设备语义和评分路径则不同。新适配器使用寄存器契约派生的完整输入，独立编译当前候选，并通过 APB 主动 Master、接口时序检查和寄存器状态模型评分。没有让路由任务的通过凭据自动授权寄存器任务。

| 层次 | 本阶段使用的依据 | 不能推出什么 |
| --- | --- | --- |
| 原生交互机制 | 字节完全一致的 worker、controller、Session 及既有实际 SDK 验收；每条试次再次检查安装和隔离表面 | 不能推出新的设备行为正确 |
| 新评分适配 | 17 项实际检查，包含公开／终局／保留分派、候选身份、20 动作和两次测试边界、提交停止、故障分类与恢复 | 不能代替具体实例功能对照 |
| 具体契约 | mixed 与 status 各两种合法结构通过，分别拒绝 8 与 5 个适用功能负例；原始记录重新审计 | 不证明全部合法参数或所有错误都已覆盖 |
| 真实求解 | mixed 一条独立模型会话、初始模板、实际工具反馈与独立终局评分 | 不构成任务族难度排名或训练收益证明 |

四项实际文件篡改挑战也被准入检查拒绝：错误任务身份、错误材料清单、错误后端类型，以及缺少运行依赖。原始凭据和历史任务保持不变。运行器仍采用共享固定用户和网络命名空间、独立临时工作目录；这里没有宣称完整的对抗性操作系统隔离。

## 模型实际完成了什么

预先声明只运行一条 mixed 契约试次，使用 `deepseek-flash`、reasoning off、20 个动作、20 次模型请求上限、最多两次公开测试。采样温度沿用服务默认值，没有取得可固定种子或精确权重版本。模型开始前冻结规格、模板、运行源码、三类输入、提示与停止规则；没有按结果替换样本。

这个契约同时包含三个独立地址、普通读写、位写掩码、W1C、只读行为和两拍 Access 等待。模型执行顺序是：读取 Spec 与 RTL → 编辑一次 → 公开测试 → 提交。公开 PASS 确认进入下一次有响应的模型请求，最终提交与该候选的源码哈希一致。

| 实际测量 | 结果 |
| --- | --- |
| 动作／编辑／公开测试 | 5／1／1；没有动作拒绝 |
| 首份编辑 | 公开检查通过，之后没有再编辑 |
| 独立终局奖励 | Reward=1；582 笔访问、19 次复位、1164 个等待边沿、51 项必要覆盖 |
| 独立保留评估 | 单独通过；相同义务、不同冻结随机输入，不合并为训练奖励 |
| 公开检查活动 | 534 笔访问、19 次复位、1068 个等待边沿、51 项必要覆盖 |
| Token／整条耗时 | 7,823／118.1 秒 |
| 三次编译／三次仿真 | 约 57.2／13.4 秒实际子进程耗时；无二进制复用 |

SDK 事件记录的模型步骤间隔合计约 4.7 秒，它不是服务端纯推理耗时；其余时间还包括启动、传输和完成状态收集。API 货币费用不可取得。训练侧公开检查加终局评分有两次编译，保留评估的第三次编译单列。

候选用字节使能与位掩码的交集更新普通寄存器，用 `旧值 & ~(写入值 & 使能)` 更新 W1C，并把读回与错误状态保存在 Access 期间的寄存器中。[最终源码和实际调用](../experiments/task-space-v1/calibration-register-v1/exchange-v11/manifest.json)允许核查这一实现。未使用的内部信号不影响本任务有限功能结果；这里没有综合或资源优化评分。

这条轨迹适合作为**实际验证过的首编辑实现示例**和新任务域运行闭环证据。它没有失败反馈后的修复过程，不能标为调试成功案例，也不能据一次通过认定任务族已经饱和。

## 恢复可靠性也是可复用成本的一部分

第一轮适配器验收中，16 项检查通过，但再次收集同一完成作业时重新生成归档，造成归档身份不同。系统拒绝覆盖，原有评分未被修改。修复后将完成归档封存一次，在独立验收目录重新执行，17 项全部通过，其中包含“恢复不触发重新编译或评分”。两轮原始记录分别保留。

正式模型调用前另有一次启动检查失败，发生在 API bootstrap 送出之前；修正输入解析后重新冻结计划。因此模型分母仍为一条，不把未启动的检查算作模型失败，也不隐藏这项执行器修正。上述改动没有改变任务 Spec、激励、Oracle 或奖励规则。

新领域目前每次评分都重新编译。此次三个阶段的编译成本明显高于仿真成本，但小样本不足以估计长期吞吐量。下一步可以研究固定 VIP 与候选构建分离；任何缓存仍需完整依赖绑定及实际一致性验收，不能直接复用评分结果。

## 怎样复用运行入口

前提是合法 EDA 环境、匹配的生成材料、原生运行机制证据，以及该实例真实控制银行。个人连接配置、输入文件和完整原始日志留在可信本地。新的配置在既有 SSH 字段之外声明 `apb_vip_root` 和 `environment_entry_sha256`；后者是实际统一环境入口文件的内容哈希。

1. 按[任务族说明](../task_families/apb_register_v1/README.md)生成新材料并运行实例对照。
2. 使用 `environment.register_inputs_v1.write` 生成 public、terminal、heldout 三份输入。每个角色包含完整定向义务，随机补充分别冻结；不允许调用者删除部分义务。
3. 对新运行版本执行 `environment.register_acceptance_v1`，使用 `environment.register_admission_v1 qualify` 绑定原生机制与真实新后端证据，然后用 `admit` 将每个实例的独立对照绑定到该运行版本。
4. 冻结 `native-register-material-study-v1` 研究计划，通过 `environment.native_tools.run_register_v1` 启动明确的一条试次。已有结果目录拒绝覆盖。

```bash
python3 -m environment.register_admission_v1 verify ADMISSION PRIVATE_CONFIG
python3 -m environment.native_tools.run_register_v1 \
  FROZEN_PLAN TRIAL_ID NEW_RESULT_DIRECTORY --ask-sudo-password
python3 -m scripts.check_register_replay RAW_TRIAL --out NEW_AUDIT.json
python3 -m scripts.register_exchange FROZEN_PLAN RAW_RUNS NEW_EXCHANGE
```

适配器的 `Backend.collect` 只连接记录中的已启动评分作业，不启动第二次评分。模型进程的中断不等于可以自动重开同一条试次：仍需检查停止状态，保留原始已启动记录。

[跨域查询入口](../environment/task_pool_v1.py)读取私有索引中的明确 `{admission, config}` 配对，重新核对来源后返回可运行身份。当前实际核对了五份新路由实例和两份寄存器实例，共七份；两份仅完成对照的路由／队列组合实例仍不混入。

```bash
python3 -m environment.task_pool_v1 PRIVATE_POOL_INDEX.json
```

这轮扩张复用了模型交互机制，新增了一个设备语义域的评分与准入适配，没有为每个寄存器实例增加运行器分支。[v11 数据交付](task-rollout-exchange.md#寄存器任务的-v11-记录)继续分开训练奖励、独立评估与离线分析。下一项更有价值的能力闭环是让已有路由／队列组合契约取得对应运行准入，测量其交互义务能否被模型满足；不急于扩大相似简单寄存器题目的采样量。
