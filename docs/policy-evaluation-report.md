# Policy v1：001 X2P 固定模型对照实验

[人类阅读入口](README.md) · [策略与执行机制](observation-policy.md) · [公开证据](../experiments/policy-v1/README.md)

本实验测量同一个 RTL 任务下，允许的信息和反馈如何影响固定模型的求解行为。没有模型参数更新。原 revision 3 的功能 Spec、初始 RTL、主动 AMBA VIP、UVM Scoreboard、私有评分及保留评估均保留。

**已完成 A／C／E 各一次真实 UTM DSH 试次；终局 Reward 分别为 1／0／0，保留评估同样为 1／0／0。完整轨迹审计通过。样本量不足以比较策略成功率，而且 E 本次没有实际调用测试，因此尚未观察到详细诊断对模型修复的效果。**

## 机制验收

正式模型实验前，39 项自动化单元检查通过；发布版本新增文件名／ID 校验后为 40 项。单元检查包括敏感字段注入、字段白名单、ENV_ERROR 与 RTL FAIL 的区分、原子动作解析及非法配置拒绝。

另有 **31 项真实 UTM/VCS 机制检查通过**，见 [mechanism/result.json](../experiments/policy-v1/mechanism/result.json)。使用明确违反 Spec 的 `bad_address.sv`，共启动七次实际 grader 调用：A 一次私有评分，C／E 各两次公开测试及一次私有评分。该受控故障对照不计入 Agent 模型样本。

| 要求 | 实际证据 |
|---|---|
| A 禁止 test，后台不启动 VCS | 被拒绝后 grader 调用数未增加；A 公开次数为 0 |
| A 可直接提交错误 RTL | 私有评分真实返回 0，无公开测试前置要求 |
| C 只见判定和剩余次数 | 真实 FAIL 仅两个字段；SDK 实际输入另做轨迹审计 |
| E 允许受控诊断 | 同一故障返回类别、`address_data`、固定诊断文案 |
| 第三次公开调用被拒绝 | C／E 各实际执行两次，拒绝后调用数不增加 |
| 终局规则不随策略变化 | 三组同源 RTL、同一私有输入哈希，均为功能失败 0 |
| 禁止读取可信文件 | 调度器只允许 Spec／当前 RTL；越权路径在执行前拒绝 |
| 不直接暴露完整日志 | 投影从空对象按白名单构造；不透传异常字符串 |
| 可追溯实际 Observation | 对比控制器 trace、发送 prompt、SDK user/message 与候选源码哈希 |

ENV_ERROR 分支和模拟敏感字段泄露检查经过单元测试；没有为了验收而破坏真实许可证或服务。已有 UID/chroot/namespace 运行方式在本次真实 Harness 事件中得到核对，但没有新增完整网络隔离或对抗性编译沙箱。

## 如何解读行为与结果

A 在没有任何功能测试反馈的情况下完成两次实际编辑。首个候选的公开集成绩，是求解进程停止后才做的离线测量；最终私有评分使用第二个候选。这两个源码哈希不同，不能把“首候选公开通过”写成“首候选已通过全部私有验证”。

C 首个实际候选在公开 `reset_w_only` case 失败。研究者可看到完整结果；模型实际收到的只有：

```json
{"status":"FAIL","remaining_test_calls":1}
```

它修改后直接提交，没有用第二次测试额度。最终私有评分及保留评估都在 `channel_gaps` 发现请求接受超过 16 周期。源码中 `s_wready` 仍依赖 `aw_have`，不能在 AW 尚未到达时独立接受 W；这违反了 Spec 的独立握手及接受时延约束。公开反馈前后这项错误依赖均存在。这里是失败原因的源码与仿真分析，不代表我们知道模型修改时的内部推理。

E 在读取两份文件后，两次回复仍把 edit 与后续 test／submit 连在一起。控制器整条拒绝，随后接受它单独发出的 submit。没有从无效回复中取出 RTL 偷偷执行，也没有人工补写候选。因此，E 的实际编辑次数为 0、公开测试次数为 0，提交内容仍是初始模板，首个有效编辑候选不存在。这个试次能检验执行约束，但不能测量“详细诊断对修复的帮助”。诊断字段确实生效的真实 VCS 证据来自前面的确定性机制验收。

形式正确的提交与功能正确要分开：允许提交模板或尚未通过公开测试的 RTL，然后按真实功能结果评分。fail-fast 在确认错误后停止剩余 case，结果可判定为 0；`verification_complete=false` 表示没有跑完全部计划 case，不表示已经确认的功能错误变成基础设施故障。没有确定性错误证据、运行故障或结果无法判定时才为 null。报告只列实际执行的 case 数，不把计划数量冒充完成数量。

## 结论边界与下一步

这次工作建立并实测了可冻结、可切换、可审计的策略执行链。单次轨迹能说明模型是否调用测试、收到什么、如何修改、最终是否通过，不能支持 A／C／E 成功率排名，也不能证明“不给反馈更好”或“详细反馈无效”。C／E 的初始候选受模型采样影响；E 没有触发一次反馈，尤其不能据此归因于反馈粒度。当前是由控制器解析的文本 JSON 动作协议，工具格式遵循能力与 RTL 能力共同影响最终成绩；不是对模型纯 RTL 设计能力的隔离测量。

当前只完成每组一次正式试次，没有完成每组三次。UTM 中每次重新编译与多套工业仿真需要较长时间，本次先完成最小真实配对及证据审计。开发试跑没有混入正式分母。API Token 可由 SDK 原始事件获得，货币账单费用不可取得，记录为 null。

最有价值的下一步是两个互补实验：

1. 在冻结协议下增加完整 A／C／E 重复次数，报告工具格式合规率、实际反馈曝光率与最终成绩，保留未编辑、未测试和未提交的试次。先确认模型能稳定使用动作协议，再解释反馈策略差异；若更改工具调用协议，必须另开版本和全部组重跑。
2. 另建明确标注的修复实验：给 C／E 同一个已确认失败的起始候选和相同预算，只改变首次测试反馈的粒度。这样更直接测量反馈对修复的作用；它回答的是修复能力，不能冒充从初始模板自主生成的成功率。

不需要通过修改 001 Spec、削弱验证或故意增加隐含要求制造差异。私有奖励与保留评估虽然输入不同，仍共享生成器、VIP 和 Scoreboard，不能排除共同盲区。完整代码覆盖闭合、综合／形式证明、网络及恶意编译隔离仍不在本次已实现范围；也没有进行 RL 参数训练。

## 数据完整性与开发试跑

正式实验前的一次开发试跑发现了动作传输问题：旧解析器会在整段回复中继续寻找 JSON，可能跳过包含未转义换行的 edit，转而执行后面的 test／submit。这会混淆策略效果，不能把这种失败算作反馈粒度导致的 RTL 失败。

已改成整条响应原子解析：只接受一个动作对象；多对象、说明文字、重复字段或损坏内容整条拒绝。单个 edit 字符串允许原始换行。修复后重新冻结版本，**三组全部重新运行**。开发批次 A 的原始评分 1、C 的原始评分 0 保留，E 在发现问题后人为中止，奖励不可判定；整个开发批次均不进入正式组间比较。见 [bringup.json](../experiments/policy-v1/bringup.json) 的原因、原始结果和证据哈希，没有改写旧 verdict。

公开导出仅包含允许发布的源码、投影反馈、计数、配置、哈希和 Harness 元数据。完整 SDK 响应、验证日志及私有向量在本地可信证据中保留。每次提交都核对为模型最后一次实际生效的编辑，求解进程停止后才启动私有评分和保留评估。

## 复现与证据

先按[运行手册](mvp-running.md)准备授权 EDA、UTM DSH、SSH 与 API key，再执行：

```bash
python3 -m unittest discover -s tests -v
python3 -m environment.check_baseline
python3 -m environment.policy_experiment \
  --out .local/policy-new \
  --policies spec_only,test_verdict,test_diagnostic \
  --model deepseek-flash --repeats 1
python3 scripts/audit_policy.py .local/policy-new
python3 scripts/analyze_policy.py .local/policy-new
python3 scripts/export_policy.py .local/policy-new experiments/policy-new
```

新运行会产生新的私有输入；同一新轮次内部严格配对。要重放本次完全相同的评分输入，需要可信侧保留的冻结输入，公开仓库的哈希不能还原向量。历史执行版本可按上述提交检出；最新版本的拒绝校验与离线审计改进有单独记录。
