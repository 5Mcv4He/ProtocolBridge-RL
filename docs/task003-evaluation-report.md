# Task003：有限队列、仲裁与提交回归

Task003 已通过独立任务质量验收，并完成9条固定模型试次。它测量深度2的AW/W/AR未退休容量、读写重叠、FIFO配对、串行APB执行、轮询仲裁和复位清理。001 revision3与002的冻结规格及历史证据保持不变。

## 契约和验证

[Spec](../tasks/axil_to_apb4_queue_003/spec.md)明确：执行中和响应背压中的事务仍占容量，B/R握手后才退休；AW与W按各自FIFO顺序配对；半个写请求不能阻塞已就绪的读。仲裁只看时钟沿前的队列头，已就绪的空闲执行器须在该沿之后进入Setup；新接受请求在下一沿才可选，响应消费与新选择不在同一沿发生。这是明确的registered启动时序要求，难度分析不能把所有时序失败都归结为队列算法。

主动AXI VIP发出交叠请求，主动APB VIP提供等待、错误和内存响应。新的UVM Scoreboard以实际握手建立三条接受队列，独立预测仲裁头、APB负载及响应，维护黄金内存并核对每通道“接受=退休+复位取消”。复位取消所有内部请求和响应，已完成外部写入保留。它没有套用001的单事务配对假设，也不把参考RTL当作仿真答案生成器。

## 失败根因与中间候选

- `r01-A`：计数为1且只退休时未减至0，后续请求被写入slot1，slot0已无效，执行器不再启动。
- `r01-C`、`r02-C`：两元素数组却用不回绕的两位头指针，入队位置又由占用数决定；不能保持FIFO顺序。r02-C重复测试同一错误候选。
- `r01-E`：AR容量在APB选择时提前释放，响应未消费就接受第三笔未退休读，违反容量契约。
- `r02-A`、`r02-E`：在IDLE选择后，再等待SETUP分支才寄存PSEL，多出一周期，违反明确启动时序。首错停止无法据此判断所有后续队列功能。
- `r03-E`：退休只清slot0，不把slot1移到头部，选择逻辑却只读slot0；待处理请求被搁置。
- `r03-A`：首候选公开19case全部通过；第二次自主修改把FIFO值先赋给内部寄存器，再在同一沿把旧寄存器值赋给APB输出，非阻塞赋值造成PSEL有效时负载过期。A没有功能反馈，不能说它忽略了PASS提示。
- `r03-C`：移位队列保留容量至响应消费，正确处理同时入队/退休，独立完整评分通过。两次额外note字段先被拒绝，合法编辑后直接提交。

[独立事后探针](../experiments/task003-v1/first-candidate-probe/)已将r03-A首候选交给原轮次冻结的私有Reward和保留输入：两组均21/21case通过，分别506计划/474完成/32取消、33/33必要bin。首候选SHA-256为`e159fbc899a98512aca32c2a4be821216310bf75cb50e8bd3453483b20688e81`。因此本例有完整的“首候选通过、提交前自改引入回归”证据，不仅是公开PASS。

原始最终奖励始终基于submit版本，不用中间最佳候选替换。具体代码、实际公开观察和全体试次来源见[发布证据](../experiments/task003-v1/pilot/)。私有向量、完整商业日志和原始模型回复只保留在可信环境。
