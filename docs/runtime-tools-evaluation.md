# 从错误类别到实际握手：运行时实验研究

本轮固定 Task003，新增两种受控开发实验反馈配置，研究模型是否会主动运行实验、读取事件、修改相关状态逻辑并通过独立验证。没有新增更难的 RTL 任务：历史 Task003/004 已持续暴露容量和并发更新问题，当前更需要测量调试过程，而不是继续抬高设计难度。

工具实现、权限、数据字段和复现命令见[运行时实验接口](runtime-experiments.md)；全部公开数据索引见[证据目录](../experiments/runtime-tools-v1/README.md)。Task001–004 的规格、模板、Scoreboard 和终局评分语义均未修改。

## 方法与冻结

运行源码冻结于 `22e2410`。两组都是 E 基础策略，允许相同的 experiment/observe 动作；`runtime-verdict-v1` 返回实验判定，`runtime-observe-v1` 额外返回固定需求诊断和真实引脚时间线。两组权限、预算和 Prompt 对照通过：Prompt 只切换反馈模式值。

每组一条真实 `deepseek-flash` / DSH `0.2.2rc2` 修复试次，动作协议为 `text-json-atomic-v2`。起点均为此前真实 Agent 生成且功能失败的[最终候选](../experiments/synthesis-tools-v1/candidate-10.sv)，SHA-256 为 `27fa0729dd5f5bd0e84cf4199e66bd445610efb7bd8c2877f13482b08bb6402d`，研究者没有修补它。它曾通过综合及自身网表等价检查，但违反未退休请求容量限制；没有证明它只有这一种缺陷。

两组使用相同 Spec、相同起点、相同公开集、相同冻结私有 Reward 和保留输入，新会话、新工作区，单并发。每条 20 动作、2 次完整公开测试、3 次实验、4 次查询；模型输出上限 7000 tokens，reasoning off，temperature/seed 为供应商默认，非确定性。顺序预先固定为判定组再时间线组，没有做顺序平衡。模型启动前保存了[实验计划](../experiments/runtime-tools-v1/study-plan.json)，最多两条，不根据结果追加成功样本。

这是**详细运行时反馈组合**的探索，不是单独引脚时间线的因果消融：详细组也获得 Q_CAPACITY 等固定需求提示。两个条件均比历史 E 多出三次实验额度，不能与旧批次直接合并比较。

## 真实验收及能证明的范围

- **Task003 完整准入**：两种合法实现分别通过完整 21 case 与公开 19 case；15 个错误对照被检出；40 项 Policy 机制检查和隔离探测通过。
- **新工具冻结版 41 项实测检查通过**：正确参考在写 FIFO、读 FIFO、AW 半包、仲裁及响应等待中的复位场景通过；观测得到合法的接收/退休计数；提前释放信用与错误队列头的负对照实际 FAIL。
- **观测不干扰的检查**：write_fifo 场景中，加观测和不加观测的整个单 case 判定、事务账目、信用账目和覆盖结果相同。其他四个场景的带观测正参考也通过；这不是对所有候选、所有事件调度的形式证明。
- **主动实验接口**：自定义读写事务实际通过；真实 Session 运行三次实验、查询采样，第四次实验被拒绝，私有场景、读取前调用和提交后调用被拒绝。
- **分类边界**：禁止的 RTL 返回 INVALID，缺失配置返回 ENV_ERROR，两次独立探针均未进入工具执行阶段。敏感字段投影、严格参数验证、预算、截断及训练/评估分区另有自动化测试。

原有私有评分完全不加载实验副本或观测代码。实验的内部 case 判定可以 PASS，但实验记录的 `reward` 始终为 null；数值终局奖励只能由提交后的原验证器产生。

### 实际抓到的容量事件

以下来自已知错误控制 `bad_early_credit.sv`，不是 Agent 试次，也不是根据源码画出的假想波形：

| 实际周期（pre） | 接口事件 | 未退休 AW / W / AR |
| --- | --- | --- |
| 14 | AW、W 接受 | 2 / 2 / 0 |
| 15 | APB Setup | 2 / 2 / 0 |
| 16 | APB 完成 | 2 / 2 / 0 |
| 17 | 再次接受 AW，尚无 B 退休 | **3 / 2 / 0** |

同一周期原检查器报容量错误。[对应事件证据](../experiments/runtime-tools-v1/observed-capacity-counterexample.json)绑定了控制 RTL、观测器与原始记录哈希。这里的计数由已确认的接口握手独立累计，不读取 DUT 内部计数器；X/Z 引脚会显式显示 null。Agent 可以检查代码自己的计数含义是否与这些外部事件一致。

## 两条真实修复轨迹

| 条件（各启动 1 条） | 有效提交 | 功能成功 / 终局奖励 | 保留评估 | 动作 / 编辑 | 公开测试 / 实验 / 查询 | 动作格式错误 |
| --- | --- | --- | --- | --- | --- | --- |
| runtime-verdict-v1 | 1 | 0/1，0 | 0 | 13 / 1 | 2 / 3 / 4 | 0 |
| runtime-observe-v1 | 1 | 0/1，0 | 0 | 12 / 2 | 2 / 3 / 1 | 0 |

全部启动试次都保留在分母中。两条均获得公开失败反馈、形成有效编辑并提交；没有基础设施失败或 Reward=null。两组的首个编辑候选均在实际公开测试中 FAIL，最终提交均在独立私有评分及保留评估中确认 `Request capacity exceeded`，分类为 `protocol_timing_error`。遇到确定错误即停止，所以这两份错误候选各实际执行了 1 个终局 case 和 1 个保留 case，不能称作各跑完了 21 case。详细组最后一次编辑之后没有剩余公开测试结果，最终判定来自私有评分。

两组使用的**同一对冻结私有输入**另经正确参考真实复验：Reward 与保留集各 21 case 通过，各 506 笔计划事务、474 笔正常检查、32 笔复位取消，33/33 个需求覆盖桶。此复验发生在求解进程停止后，没有回流给 Agent，也未重新评分候选。见[输入验收](../experiments/runtime-tools-v1/input-qualification.json)。

### 判定组：修改了代码，但退休边界仍然错误

模型先测试失败，再运行 address_data / write_fifo 局部实验，重复查询得到的仍是判定与剩余额度。第 9 动作编辑加入 `b_pop/r_pop`，收紧了部分 READY 条件，但实际信用计数仍在 APB 启动时递减，而不是 AXI 响应握手退休时递减。后续公开、局部及私有验证继续报容量错误。源码还去掉了部分待消费响应对执行的限制；这可能引入其他问题，本轮没有隔离证明每个潜在回归。

### 时间线组：真实证据已曝光，未形成有效修复

第 4 动作运行 address_data，收到真实采样和 Q_CAPACITY：周期 13、14 连续接受两笔 AW/W；周期 15 在 APB Setup 时又接受一笔，未退休 AW/W 变成 3/3，没有 B 退休。第 7 动作修改后，第 9 动作重复实验的错误窗口**逐行引脚记录完全相同**。

第一次编辑主要整理组合逻辑，将队列弹出条件提成 `aw_pop/w_pop/ar_pop`，但仍将 APB 启动作为释放信用的事件。第二次编辑主要调整注释及单句 begin/end，未修正该容量逻辑。这是基于源码差异与实际错误窗口的判断，不是全设计形式等价证明，也不能据此断言模型内部如何推理。

模型确实调用了一次自定义单写事务并得到 PASS，但该事务**直接沿用 Prompt 中的示例**，不能据此声称自主设计了最小反例。该次实验的默认输出落在周期 52–58 的空闲尾部；随后查询周期 0–7，仅看到复位。单笔通过也不能反驳多笔未退休容量错误。最后一次局部实验申请因三次额度已耗尽被拒绝，后台没有启动第四次仿真。

因此要区分四件事：工具被调用、有效信息被返回、信息被用于正确诊断、修复通过。前两项在详细组有证据，后两项没有。本轮没有由研究者代写代码，也没有对非法动作作静默修复。[行为证据](../experiments/runtime-tools-v1/behavior-evidence.json)记录了源文件、真实结果和窗口对照哈希。

模型请求时间是 SDK 请求的墙钟时间，不是服务端纯推理时间。编译/仿真统计包含公开、实验、终局及保留执行；独立准入和正确参考复验不计入这两条试次成本。实验工具时间是其中的子集，不能再次相加。金额无法取得，未估造 API 费用。当前成本主要在编译，不能将整条耗时都归为模型思考。

每组经验成功率 0/1，Wilson 95% 区间为 0–79.3%。样本不能判定时间线有效或无效，不能给出策略优劣排序，也不能校准任务难度。两条奖励均为 0，当前样本没有组内终局奖励差异；这不等于任务对所有 RL 算法都没有价值。轨迹仍明确区分了格式合规、真实工具使用、无关窗口查询、局部 PASS 与未修复的终局错误，可支持调试行为评估及后续数据策略研究。当前没有模型参数训练。

交换 Schema v3 已从实际原始记录重新审计导出：本轮 2 条加此前综合工具 1 条，共 3 条，分别保留实验身份，**不合并成功率**。`synth_check`、`experiment`、`observe` 的实际动作与受控反馈进入工具轨迹；保留评估、包含保留执行的整体成本和离线分析放在独立分区，不作为求解时反馈。原始日志与私有向量不公开；v1/v2 历史交付保持不变。该交付没有 token 级 logprob 等信息，不是无损 on-policy 训练记录。

## 当前限制与最近下一步

1. 运行时工具仅验收 Task003。没有任意内部信号访问、GUI 波形工具或 Agent 自建可执行 SV Testbench；当前是固定接口引脚采样和受控事务请求。内部仲裁决策只能从后续接口行为推断，不能冒充直接观察。
2. PASS 的默认尾部窗口可能只显示排空后的空闲周期；查询依赖 Agent 自己选择周期，没有按“首次 AW 接受/首次 B 退休”导航。下一版最值得先改的是**基于真实事件索引选择窗口**，并以本次 PASS 只见空闲的记录作正反例验收。
3. 当前 Agent Prompt 给出了事务字段和范围，但没有完整说明 VIP 各延迟字段的参照事件。文档已明确实际语义，冻结 Prompt 没有中途修改。后续版本应把精确刺激契约也给 Agent，再做匹配条件下的修复试次。
4. 最多 4096 周期采样，超限明确标记；每次最多 24 行。不能从有限窗口声称解释所有失败。自定义场景沿用 reactive READY，不能任意控制全部引脚或构造非法协议。
5. 本次没有扩展 Task005，也未将教学库测量转为 PPA 奖励。已有 003/004 难点尚未解决，先改善可验证的调试过程比再提高难度更有价值。

单元测试 107 项通过；历史基线核对通过（该命令不执行仿真）。上述工业验收、两条真实试次及独立输入复验是另行实际运行的证据。后续应冻结新观察版本，先验证事件窗口是否确实展示接收到退休的关键过程，再以同一失败起点作小规模对照；当前不扩大模型调用。
