# 功能保持的结构优化：更少单元之前，先保证结果不变

一个实现能够算对，并不意味着它已经满足工程资源约束。反过来，电路变小也可能只是因为遗漏了功能。这个任务将两种判断分开：Agent 修改一个统计 8 位输入中 `1` 数量的组合模块，可信侧先验证完整功能，再测量固定综合流程下的映射单元数量。

**任务已完成15项工业验收与一条真实模型试次。** 两种合法结构分别得到22、19个单元，证明门槛可达；模型首个测试候选得到23个单元且功能正确，后续被测试版本却破坏功能，最终奖励为0。这个样本展示了可审计的优化回归，不证明稳定难度，也不证明增加指标反馈就能改善结果。

## 这个任务究竟优化什么

`bitfold_cell_budget_v1` 的输入是8位 `data`，输出是4位 `result`，必须对全部256种输入返回准确位计数，不允许状态或锁存器。Agent 获得功能正确但结构超额的起始RTL，交付完整 `bitfold.sv`。它可以读、改、公开测试和提交；不能更改综合约束、库、参考设计或判据。

指标是 Design Compiler 完成映射后的单元实例数，上限22。固定流程使用教学库 `class.db`、10单位虚拟时钟、0.1输入／输出延迟及 `compile -map_effort medium`。脚本、库内容哈希和实际工具版本均记录；库文件不公开分发。该数值不是面积、等效门数、功耗或真实芯片PPA，不承诺其他工具版本得到同样结果。

在定义任务前，按[六次可行性探针](../experiments/bitfold-optimization-v1/feasibility.json)比较四种功能正确的表达方式：串行累加23、查表19、平衡树22、并行位运算33。再次测量19与33，数量保持一致。它证明当前流程中存在改进空间，不证明所有RTL映射都稳定，也不说明查表总优于其他结构。初始33与目标22来自这次工程可行性判断，未通过模型预跑挑选起点。

## 工具判断与任务判断怎样分工

[独立评分包装](../verifier/bitfold_optimization/campaign.py)复用既有位计数后端，不修改旧任务：

1. VCS执行独立整数判据，每阶段用三种输入顺序检查全部256种输入，共768次检查。
2. DC确认完整映射且没有寄存器或其他状态。
3. Formality比较候选与独立可信参考，判断候选是否保持指定功能。
4. Formality比较候选与它自己的综合网表，检查综合变换一致性。
5. 以上均完整通过，且库哈希一致，才读取唯一的 `PB_CELLS` 计数并比较上限。

独立参考与自身网表是不同关系；第二种等价不能代替第一种。功能错误直接得到功能失败，不能凭较小结构拿到成功奖励。工具故障、不完整比较和无法确定的测量保留null；无效提交另行分类。资源超额是明确任务失败，使用 `synthesis_error` 类别与具体 `mapped_cell_budget_exceeded` 原因。

15项门禁包括两个合法实现各三个阶段、两个功能正确的资源超额对照、三个功能错误、三个无效输入和一个语法错误。**功能负例实际进入功能检查后被拒绝**，没有把编译失败算作检错。总计12次编译，完整门禁约100.24秒。阶段输入顺序不同，但有限输入空间均已穷举；保留评估是独立重跑，不能称为新功能域或长期未见测试。

当前验收使用VCS O-2018.09-SP2、DC与Formality O-2018.06-SP1。来源门禁严格匹配源码与库；复现时仍需核对工具版本，不能将该证据直接搬到另一版本。没有建立任意工具二进制及其所有内部库的通用依赖解析器。

## 一条真实轨迹揭示了什么

[计划](../experiments/bitfold-optimization-v1/study-plan.json)在首次模型调用前冻结：deepseek-flash、reasoning off、最多20个工具动作和20次模型请求、4次公开测试、仅1条试次。温度由服务默认值决定，没有固定随机种子或精确权重身份。Session v6只增加受控结构测量字段，使用已验收native v3工具入口；与旧反馈条件分别记录。

| 实际动作 | 可核查结果 | 可以判断什么 |
| --- | --- | --- |
| 首次编辑后测试（动作4） | 功能与两类等价通过，23个单元，资源FAIL | 从33降到23，但仍未满足22上限 |
| 后续测试（动作8、12、14） | 三份不同源码均功能FAIL | 在已有正确功能之后，发生已验证的功能回归 |
| 最终编辑与提交（动作15、16） | 最终版本未公开测试；终局0、保留0 | 最后修改未解决独立评分发现的功能问题 |

总计8次有效编辑、4次公开测试、1次格式拒绝。四份测试反馈均核对到后续实际模型请求；拒绝动作没有修改源码。8个编辑版本中4个被公开测试，另有3个未测试中间版本和1个未测试最终版本。本研究没有事后评分这些中间版本，也没有用私有结果替Agent选择提交。

具体而言，首候选用逐位累加保持了位计数。后续测试版本把各输入对的异或／进位拼成二进制向量并直接相加，混淆了“多个同权计数项”与“不同位权的二进制数”；独立检查返回功能不一致。最终候选也未通过位计数检查。这是源码与实际测试共同支持的工程解释，不是对模型内部思维的推断。

首次反馈明确送达了“功能正确、23、上限22”。后续功能失败时不返回结构数量，避免诱导使用无效功能的较小结果。完整反馈、拒绝、候选与终局由[离线重放审计](../experiments/bitfold-optimization-v1/replay-audit.json)核对，无额外模型或EDA调用。

## 成本、数据用途与下一步

这条试次报告44,927 Token，整体65.95秒。四次公开检查加终局、保留共六次编译：编译13.32秒、仿真6.09秒；综合5.23秒，两类等价分别1.39和1.81秒。功能失败会提前结束后续证明，因此这些时间不能当作六次完整优化评价的固定成本。模型步骤时间包含网络与Harness等待，货币费用不可取得；详见[成本记录](../experiments/bitfold-optimization-v1/costs.json)。

轨迹适合研究功能保持、优化回归和最终验证决策，不是成功优化示范。初始功能正确与资源失败须分开表达：如果只看终局0或四次FAIL，会漏掉首候选确实保持功能并减少资源这一事实。[新版用途规则](trajectory-data-uses.md#原生轨迹的独立用途审查)据此增加功能回归标签，但不把它自动当作有效训练数据。

下一步最有价值的是在固定起点上研究受控功能反例是否帮助维持正确性，例如公开失败的输入、期望与实际输出；应另行冻结反馈版本与匹配试次。本阶段没有实施该对照，也没有增加模型样本来追求成功。任务仍是一个人工审阅的固定流程契约，尚未扩展为任意位宽／任意库优化生成器。
