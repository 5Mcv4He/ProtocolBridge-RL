# 路由任务族：生产方法、一次真实漏检与验收

本轮研究的问题是：已经可靠验证的一道 RTL 任务，能否被特化成新的工程契约，并继续产生可信奖励？首个任务族固定三目标、单事务 AXI4-Lite → APB4，只改变地址窗口。它测量任务生产方法，不将地址组合数量当作独立工程能力数量。

**最重要的发现是一个真实漏检。** 一份明确违反新 Spec 的错误 RTL，在旧生成验证器下通过了 27 个 case 和全部 1,728 个必要交叉覆盖 bin。它没有进入正式 Agent 评测：生产过程中的语义审查发现缺口，随后为新窗口内部的地址变化补充了实际激励和专门错误对照。这个例子说明，复用成熟验证组件仍须重新检查参数变化带来的验证义务。

[生产机制与具体地址实例](task-family-production.md) · [生成与运行方法](../task_families/router_v1/README.md)

## 为什么边界检查仍会漏掉窗口中段

irregular 契约的目标 0 接收 `0x00021000` 到 `0x00023fff`，容量为 12 KiB。它的 APB 局部地址必须等于全局地址减去 `0x00021000`。一个常见错误是套用只适合特定对齐、二次幂容量的掩码捷径：

```systemverilog
local_address = (a - 32'h21000) & 32'h2fff;
```

`0x2fff` 是 12 KiB 减一，但它把偏移中的 bit 12 清零。于是中间 4 KiB 会被错误映射回前一个区域，首尾地址却仍可能正确：

| AXI 地址 | Spec 要求的局部地址 | 错误实现的局部地址 |
| --- | --- | --- |
| `0x00021000` | `0x00000000` | `0x00000000` |
| `0x00022000` | `0x00001000` | `0x00000000` |
| `0x00023ffc` | `0x00002ffc` | `0x00002ffc` |

旧生成方法复用了 Task002 的协议流量，再增加窗口端点与全局地址位翻转。全局地址翻转与局部偏移进位并不是同一件事：翻转基地址 `0x00021000` 的 bit 12 会得到窗外的 `0x00020000`，而窗口内偏移 `0x1000` 对应的是 `0x00022000`。继承流量仍集中在旧的较小偏移范围，新增点也没有访问这个中间区域。真实探针的 6,003 笔计划事务中，5,949 笔完成检查，54 笔被复位取消；整个仿真返回了 Reward=1（[仿真摘要](../experiments/router-family-v1/calibration/old-verifier-result.json)、[错误 RTL](../experiments/router-family-v1/calibration/faulty-offset-mask.sv)、[源码绑定与反例](../experiments/router-family-v1/calibration/gap-analysis.json)）。这是**验证器覆盖缺陷造成的错误奖励**，不是模型成功，更不是能力饱和的证据。

Scoreboard 的地址判据本身能够发现这个错误，但前提是实际执行相关请求。原有交叉覆盖关注目标、字节使能、写半部先后、错误、等待和背压，没有声称覆盖全部地址。**一个维度的覆盖全满，不能补足另一个未被采样的工程维度。**

## 修正针对的是验证义务，Spec 没有改变

生成器现在对每个窗口内的二进制偏移进位点及其前后一个字执行读写，同时把经审阅的语义锚点地址也送入实际 DUT。新增错误对照会丢失局部地址 bit 12；irregular 的该对照与上述漏检探针是完全相同的源码，而不是重新制作一个更容易检测的错误。

单看写后读数据一致，也可能漏掉地址别名；本次由 Scoreboard 逐事务比较预期局部地址与真实 APB 地址，报告了[地址不匹配](../experiments/router-family-v1/calibration/detection.json)。

这里有两项互补的检查。语义锚点验证可信端的译码函数是否符合事先审阅的地址事实；实际事务激励检查候选 RTL 是否实现这些事实。前者不能代替后者。原有两个合法参考、十三种错误对照、复位与协议检查仍保留，新增对照使每个最终候选需要检出十四种明确违例。

为了实际检查两者的边界，另建副本，把参考实现和 Scoreboard 的目标 0 上界同时缩短，让二者犯相同错误。编译成功，但仿真初始化时的独立锚点发现可信译码与审阅契约不符，返回 `infrastructure_error / reward=null`（[注入与结果](../experiments/router-family-v1/calibration/oracle-fault.json)）。此时不能给候选 0 或 1，因为作为裁判的验证环境本身已经不可信。这是单独的验证器故障探针，不是 Agent 失败，也没有修改已经准入的包。

此修正仅作用于新生成包。Task001–004 的冻结 Spec、源码与历史结果保持原样。生成方法及包清单独立冻结，旧的漏检结果、原始源码和未获准入的候选继续保留。

运行使用 VCS `O-2018.09-SP2`、AMBA VIP `R-2020.12`、UVM `1.2`；控制器与工作进程的 Python、Harness 版本见各份 `quality/freeze.json`。113 项本地单元检查和每包 107 项生成前置检查通过；[一次全新重建](../experiments/router-family-v1/reproduction.json)得到相同清单字节。后者是生成可复现性检查，不是一次新的 RTL 仿真。

## 一次真实求解说明了什么

在启动模型前冻结三份包、生成版本与试验计划，预先选择 irregular 作为代表：它同时具有非二次幂窗口、非地址排序的目标编号与高位译码。本轮只计划一次 `deepseek-flash` 独立生成，不因成功或失败追加样本；使用 DSH `0.2.2rc2`、`text-json-atomic-v2` 和 E：Test-diagnostic，最多 20 个动作、两次公开测试。模型只获准读取 Spec 和 RTL、编辑 RTL、调用受控测试及提交；参考、验证源码及私有输入不属于求解观察。

实际轨迹是 **read Spec → read RTL → edit → test PASS → submit**。五个动作全部合规，一次编辑形成首个候选。公开测试的 PASS 已在下一次模型请求中送达，随后模型提交了同一份源码，没有修复或第二次测试（[逐动作轨迹](../experiments/router-family-v1/pilot/r01-test_diagnostic/trace.json)、[候选 RTL](../experiments/router-family-v1/pilot/r01-test_diagnostic/candidate-03.sv)）。

| 测量 | 结果 |
| --- | --- |
| 启动 / 完成 / 有效提交 | 1 / 1 / 1 |
| 首个候选公开测试 | PASS，22 case |
| 独立私有 Reward | 1，27 case |
| 保留评估 | PASS，27 case |
| 动作格式错误 / 拒绝 | 0 / 0 |
| 公开反馈曝光 / 失败诊断曝光 | 1 / 0 |
| 收到反馈后的编辑 | 0 |

模型使用完整范围比较与减基地址实现译码，独立保存 AW/W 两个写半部，并把 APB Setup、Access 与 AXI 响应状态分开。源码没有采用上述错误的 12 KiB 掩码捷径。终局与保留各有 6,115 笔计划事务、6,061 笔检查完成和 54 笔复位取消；源码与输入冻结保持不变，求解进程在私有评分前已停止。[审计结果](../experiments/router-family-v1/pilot/audit.json)还核对了实际送入 Harness 的观察、工具预算和提交身份。

研究侧随后让合法参考运行这条试次的**完全相同的冻结私有输入**，Reward 与保留两组均通过，并核对输入哈希一致（[独立输入核验](../experiments/router-family-v1/input-qualification/result.json)）。这是对评测条件的额外检查，不是重新评分模型，也没有把私有反馈交回求解进程。

这一结果支持“生成包能通过统一入口完成真实求解与独立评分”。它不支持“详细诊断提高修复能力”：虽然 E 允许诊断，本次只暴露 PASS，没有功能错误反馈，也没有修复行为。1/1 只是本次观察，不能估计整个任务族的成功率、判定能力饱和，或与历史 Task002 的不同批次合并比较。

原始模型事件、源码版本、公开结果及私有原始输入留在可信存储；公开导出保留实际反馈、候选、提交、哈希和评估摘要。这条试次尚未加入历史 v1–v3 轨迹交换集合，不改变其既有 88 条记录的统计。

## 从生产过程得到的约束

另一次早期候选在 RTL 正反对照都符合预期后，被反馈机制验收拒绝：把新增边界场景放到最前面，改变了受控诊断所依据的首个失败场景。修正保留了原有场景顺序，再追加新检查，没有放宽权限或删除机制断言。[早期门禁拒绝摘要](../experiments/router-family-v1/calibration/prototype-rejection.json)保留了这一失败。

包内静态检查也发现，直接复制旧测试会留下旧地址、旧 case 数量和旧日志契约。现在生成包必须先完成对应的单元检查，失败时保留候选并停止，不能直接把它送入正式模型评测。生产过程因此需要同时维护工程规格、验证语义和环境接口，而不只是生成可编译的 RTL 文件。

## 生产成本与下一步瓶颈

三份最终门禁分别用时约 934、931、971 秒，合计约 47.3 分钟。每份均包含正反对照与真实环境机制检查；原有错误对照可以合并编译，确认缺陷后提前停止。这个成本属于任务准入，不能与一次 Agent 求解的成本混为一谈，也不能从总耗时中扣除不成功的开发候选。完整[成本清单](../experiments/router-family-v1/costs.json)另列早期被拒候选、覆盖缺陷探针、模型前置检查与私有输入核验。

一次实际模型试次用时 **538.3 秒**，五次 SDK 请求区间合计 **18.4 秒**；后者包含 Harness 与网络开销，不是纯模型计算时间。SDK 报告 15,433 总 Token，其中非缓存输入 2,484、缓存读取 10,752、输出 2,197；没有取得货币费用。公开、终局、保留验证复用了同一候选的合格编译产物，实际有一份编译日志和 76 份仿真日志。日志中的数值尾注合计记录编译/链接 CPU 时间 82.134 秒、仿真 CPU 时间 105.460 秒。

这个后端没有分别记录编译和仿真的墙钟时间，因此相关字段为 `null`，不能把 CPU 秒当作等待秒，也不能把剩余总耗时都归为某一种工具。模型会话首尾跨度还包含公开测试等待，不能将它当成推理耗时。[试次测量摘要](../experiments/router-family-v1/pilot-summary.json)保留测量口径和来源。

目前源码包继承完整基础快照，以换取保守、容易核对的执行一致性；[源码体积记录](../experiments/router-family-v1/source-footprint.json)用于衡量这种副本成本。下一步可在第二类任务族中实测哪些协议、驱动、判据和环境组件真正独立，再细化依赖冻结；不能为了减少重复编译，直接跨不同源码或工具链复用准入和二进制。

## 如何核查和复用

[证据入口](../experiments/router-family-v1/README.md)按问题连接清单、源码、正反例、实际反馈、审计与成本。生成器以固定 Git 基础提交重建完整包；[使用说明](../task_families/router_v1/README.md)给出生成、reset、工业门禁和真实 rollout 的命令。生成或核对公开哈希不需要 EDA，也不等于执行了新仿真。复跑工业验证需自备合法工具环境；原始私有向量和完整商业日志不随公开仓库分发。

## 结论边界

三个配置属于同一有限路由任务族，初始接口一致，参考实现去除地址常量后的结构也一致。它们是参数化工程契约，不是三个新协议，也不构成三个独立能力维度。当前只接受经审阅的三种配置，任意参数、目标数扩展、队列组合及通用自然语言 Spec 生成均不在这一版本范围内。

有限仿真、错误对照和锚点检查仍不能证明验证完备。参考实现与验证代码公开也带来潜在预训练污染；求解进程无法读取本地答案，并不证明模型过去从未见过相关设计。任务难度需要真实试次分布校准，不能从一次成功或失败下结论。

后续最有价值的生产改进，是把“契约变化 → 新的可观察边界 → 对应错误对照”变成可复用的验收方法，并测量每份准入与有效轨迹的成本。扩大参数组合数量应建立在这些证据之上。
