# 队列任务族：动态验证义务与事件工具研究

本轮把任务生产从静态地址路由扩展到时间与状态管理：当队列容量改变时，能否同时产生清晰契约、适用的错误对照、实际触发的验证义务和可执行的 Agent 环境？三个有限队列契约已经完成来源绑定的工业准入，三条真实模型试次得到 0、1、0。一个值得追踪的现象是：增强工具试次的首候选事后通过公开验证，后续未经测试的编辑却引入了调度回归。

这不是工具效果或任务难度的排名：每种条件只有一条，增强条件还存在 Prompt 差异。三个包属于同一能力族的参数化实例，不能直接作为三个独立能力。

[先理解生命周期与生成方法](queue-family-production.md) · [证据目录](../experiments/queue-family-v1/README.md) · [事件导航接口](runtime-events-v2.md)

## 为什么选择一名额、三名额与不对称容量

历史 Task003/004 的模型失败反复涉及提前释放信用、请求身份、FIFO 更新与响应退休。本轮没有继续叠加 Burst 或多目标并发，而是保留 Task003 的执行规则，分别选择 AW/W/AR 容量 1/1/1、3/3/3、1/1/3。这样可以观察最小的方向独立容量、非二次幂存储使用与读写资源不对称。

这不等于只改一个数组大小。接受请求、APB 完成与 AXI 消费响应是不同事件；直到最后一个事件才释放未退休名额。一个名额仍允许独立读写和未配对的写半部，因此不等于 Task001 的全局单事务。另一方面，本族仍等待当前响应被消费再调度下一笔 APB，没有引入 Task004 的执行解耦。

两个合法参考分别使用环形索引与移动数组。前者可以保守地下一周期再复用释放的名额，后者支持同周期退休和接受；Spec 允许二者，验证器不得强制其中一种内部结构。

## 从义务声明到真实行为证据

容量参数首先派生三组义务：各级占用与上限、多轮使用有限存储、退休边界。每组明确连接激励、独立判据、实际覆盖和错误对照。比如深度三不仅需要出现三笔已接受请求，还要在同一复位区间内反复接受和退休不同请求，核对回绕后的地址、载荷与顺序。

[来源绑定的报告器](../task_families/report.py)从冻结参考和错误对照重建实际编译集合，核对 SHA-256，再将义务所列覆盖项与两种参考的真实 case 结果逐项比对，并确认对应负例得到 0。只有声明、没有观测记录时，报告器拒绝生成通过摘要。哈希用于追溯，不参与判断 RTL 功能对错。

这里的“多轮”是实际接口接受计数，不是读取 DUT 内部指针。必要覆盖要求退休时存在待接受请求，但没有要求保守合法参考必须同周期接受它。有限覆盖、两个参考和错误对照仍不能排除其他并发交错与共同规格误解。

## 可信检查器失效时，不能强行产生功能奖励

另一个账本仅从 AW/W/AR 接受、B/R 退休和复位更新数量，逐边沿与 Scoreboard 队列长度比较。它不调用候选内部计数器或 Scoreboard 的出入队函数。每次成功仿真还必须有账本实际执行的标记，而不仅是源码中存在一个检查 task。

在独立副本上进行了[两类验证器故障注入](../experiments/queue-family-v1/oracle-faults.json)，不修改已准入包：

| 实际运行 | 候选 | 结果与依据 |
| --- | --- | --- |
| 正常验证器 | 已知提前释放 AW 信用的 RTL | `0 / protocol_timing_error`，确认接口容量违例 |
| Scoreboard 在 APB 完成时也错误出队 | **与上一行完全相同的 RTL** | `null / infrastructure_error`，独立账本报告分歧 |
| 移除账本调用钩子 | 合法参考 | 仿真走到结束，但缺少执行标记，返回 `null` |

前两次候选 SHA-256 完全相同。因此结果差异不是换了一份更容易检测的设计，而是可信判据的可用性发生变化。第三次说明“仿真结束、其他检查没报错”不能代替必要检查已经执行。

这是主动注入的可靠性研究，不是新发现的一次历史错误奖励，也不是三条 Agent 失败。执行标记证明检查钩子确实运行过，尚不能证明任意局部删改后的逐周期完整性。账本仍共享规格和接口采样，不能消除所有共同理解错误；容量事实另有经审阅的锚点，有限正反对照也不能证明验证完备。

## 事件工具：先验证能看见，再研究能否修复

历史修复试次已经显示，成功实验的默认窗口可能落在空闲尾部。对同一份真实历史记录作事后重放，旧投影的窗口包含 0 行事务事件，新投影包含 7 行（[重放证据](../experiments/queue-family-v1/tools/historical-window-replay.json)）。这没有启动新仿真，也没有让历史 Agent 看到新反馈，不能被说成一次成功修复。

新的 `runtime-events-v2` 在三名额包中完成了 [48 项真实工具验收](../experiments/queue-family-v1/tools/acceptance.json)：合法读写、部分写、仲裁、复位，容量与地址错误，成功窗口、退休事件选择、缺失事件、查询预算和权限，以及观测前后判定与事务账目一致性。单独运行的[合法参考实验](../experiments/queue-family-v1/tools/actual-event-navigation.json)确实能按 `B:0` 定位退休，而非要求模型猜一个绝对周期。

已知提前释放信用的错误实现产生了以下[真实接口事件](../experiments/queue-family-v1/tools/capacity-counterexample.json)：

| 周期 | 事件 | 未退休 AW / W / AR |
| ---: | --- | --- |
| 13 | AW、W 接受 | 1 / 1 / 0 |
| 14 | AW、W 接受 | 2 / 2 / 0 |
| 15 | AW、W 接受；APB Setup | 3 / 3 / 0 |
| 16 | APB 完成；尚无 B 退休 | 3 / 3 / 0 |
| 17 | 再接受 AW；BVALID=1、BREADY=0 | **4 / 3 / 0，违反容量三** |

这条轨迹把错误发生的过程具体化：外设完成不能释放尚未被 AXI 消费的名额。它属于工具正反对照，不是模型试次。Agent 是否实际调用实验、看到相关窗口并正确修改状态更新，仍必须另看真实求解记录。

此版本仍限制为固定接口采样与结构化事务，不能查询任意内部信号、执行自建 SV Testbench 或修改私有验证器。旧观察版本保持不变；没有把所有工程工具合并到一个新配置，也没有将实验 PASS 当成终局奖励。

## 模型能否完成生成任务：先看真实行为

研究计划在模型调用前固定三条新会话：最小容量基础 E、三名额基础 E、三名额 E 加事件实验。统一使用 `deepseek-flash`、DSH `0.2.2rc2`、`text-json-atomic-v2`，reasoning 关闭、服务端默认采样；未固定 temperature 或随机种子，不声称确定性。每条最多 20 个动作、2 次公开测试，增强条件另有 3 次实验和 4 次查询。没有替换失败样本或为追求成功追加试次。

三名额的两条试次使用完全相同的冻结私有奖励与保留输入。基础 E 与增强条件的工具集合不同，增强 Prompt 还保留“先测试起始候选”的提示；因此这是环境组合探索，不是仅改变窗口选择算法的严格因果对照。每种条件只有一条，不能估计稳定成功率或排序任务难度。

[完整结构化汇总](../experiments/queue-family-v1/study-results.json)保留所有启动试次，下面各行是独立条件、样本量均为 1：

| 契约 / 环境 | 首候选公开结果 | 最终私有 / 保留 | 编辑 / 总动作 | 实际公开测试 / 实验 / 查询 |
| --- | --- | --- | --- | --- |
| single / E | 0，事后测量 | 0 / 0 | 2 / 5 | 0 / 0 / 0 |
| three / E | 0，实际公开调用 | 1 / 1 | 2 / 8 | 2 / 0 / 0 |
| three / E + 事件实验 | **1，事后测量** | 0 / 0 | 5 / 14 | 2 / 3 / 0 |

三条都有效编辑并提交，动作格式错误为 0/27，无基础设施失败。增强组另有一次测试预算拒绝，未实际启动仿真；它是工具使用行为，不是 JSON 格式错误。第一条未获得功能反馈；第二条和第三条收到失败反馈后确实修改了代码。首候选事后测量不曾返回求解 Agent，也没有用它替换终局奖励。

这里的 0/1、1/1 只是观测结果。若作描述性的 Wilson 95% 区间，分别约为 [0, 0.793] 与 [0.207, 1]，远不足以推断稳定差异。readheavy 仅完成工业验收，本轮未调用模型，明确标为待校准。

求解停止后，还对[本轮精确评分输入](../experiments/queue-family-v1/input-qualification/summary.json)完成合法参考核验。两种契约各有奖励与保留输入，共四个不同的“契约—输入”组合：其中两组与原门禁实际通过的输入完全相同，复用其来源绑定证据；另两组实际重新运行完整 23 case，均为 Reward=1，事务账目和必要覆盖通过。三名额的两个模型条件共享输入，只核验一次。新增两次参考仿真共约 500.9 秒；没有重新评分或修改任何 Agent 的奖励。

### 最小容量失败：额外的 Setup 延迟

[第一条轨迹](../experiments/queue-family-v1/episode-1/r01-test_diagnostic/trace.json)进行了两次编辑、没有调用公开测试，随后提交。首个候选的事后公开验证、最终私有评分与保留评估均失败。首错是 `Registered FIFO grant/setup missing`：选择请求的边沿只进入内部 SETUP 状态，下一边沿才拉高 PSEL，比任务明确要求的注册选择／Setup 时刻晚一个周期。

这是该任务的调度时序要求，不应说成所有 AXI/APB 设计都禁止这种延迟，也不能把尚未执行到的其他缺陷当作实测根因。E 允许诊断，但本条没有获得功能反馈；两次编辑不能记为“根据测试修复”。容量减到一仍可能失败，说明这一次结果不能简单按 FIFO 深度解释。

### 三名额基础 E：失败反馈后修正生命周期

[第二条轨迹](../experiments/queue-family-v1/episode-2/r01-test_diagnostic/trace.json)第一次公开测试失败，模型读取当前 RTL、再次编辑，第二次公开 21 case、私有 23 case 与保留 23 case 均通过。首个候选在 APB 完成后直接回到 IDLE，而队列头尚未随响应退休，可能再次调度原请求；实际首错为 `APB setup without eligible scheduled request`。

[首候选](../experiments/queue-family-v1/episode-2/r01-test_diagnostic/candidate-03.sv)与[修正候选](../experiments/queue-family-v1/episode-2/r01-test_diagnostic/candidate-06.sv)的差异包含两个实质变化：增加 RESP 等待状态，响应消费后才恢复调度；将接受与退休导致的计数变化合并为一次增减运算，避免同周期非阻塞赋值互相覆盖。前者与已观察到的调度失败直接相关，后者是同时修改的状态管理逻辑，不能声称本次首错已经单独证明它失败。

Agent 实际收到的是错误类别、`address_data` 名称与受控的事务诊断，**没有看到上述完整内部报错或参考修复**。轨迹支持“收到失败反馈后修改相关逻辑、复验成功”，不能由此知道模型的内部推理，也不能排除没有反馈时它自行重写成功的可能性。

### 事件实验组：首候选通过公开验证，后续编辑引入回归

[第三条轨迹](../experiments/queue-family-v1/episode-3/r01-test_diagnostic/trace.json)先对空模板运行 `write_fifo`，得到只有复位附近信息的失败。模型随后连续进行了两次编辑，没有测试第一份实现。[第一份候选](../experiments/queue-family-v1/episode-3/r01-test_diagnostic/candidate-04.sv)在求解结束后的公开 21 case 检查中完整通过；它没有接受私有或保留评分，不能称为全面正确实现。

[第二次编辑](../experiments/queue-family-v1/episode-3/r01-test_diagnostic/candidate-05.sv)把 RESP 退出条件从“当前响应握手或已无响应”收紧为仅 `!resp_valid`。在时钟边沿的非阻塞赋值中，握手处理虽然安排清零 `resp_valid`，同一边沿的状态判断仍读到旧值 1；因此多等待一个周期才退出 RESP，后面的选择和 APB Setup 也晚了一拍。这与随后读写实验的 `Q_GRANT` 诊断、最终的 `Registered FIFO grant/setup missing` 相符。

两次候选实验分别显示：写方向在周期 22 退休 B、23 接受 AW/W，读方向在周期 34 退休 R、35 接受 AR；对应的边沿后检查未看到按契约应启动的 Setup。模型实际收到这些引脚窗口和需求解释，之后三次编辑仍保留了上述 RESP 退出条件。两个公开测试失败；最后一次编辑后的第三个测试请求因预算耗尽被拒绝，模型仍可有效提交。私有与保留评估都在首个 case 确认时序错误，未将未执行的其他 case 算作通过。

这条记录提供了**未经验证的修改引入回归、已获相关反馈但未修复关键条件**的行为证据。它不能说明“工具让模型变差”：初始候选不同、只有一条试次、Prompt 也不同。Agent 没有构造自定义事务，也未调用 `observe`，所以新增事件索引与成功默认窗口的实际能力由工具正反对照证明，尚没有模型主动利用它们的证据。

### 奖励与轨迹各自提供什么信息

本轮终局有 0 和 1，没有 null，说明这些具体试次能产生不同终局结果；但不同契约与环境不能混成一个组内奖励分布，更不能由三条推断训练收益或任务饱和。只保存分数会把 single 的初次设计失败与增强组的后续回归都压成 0，丢失它们需要不同改进策略的信息。

三条新会话与完整实际反馈已通过审计和 [v4 交换核对](../experiments/queue-family-v1/exchange/validation.json)。保留评估、事后首候选检查与求解观察分别存放，未补造模型推理或未发生的动作。数据的研究价值在于保留候选演变和反馈曝光；尚缺行为 log probability、Token IDs 与精确模型权重版本，不能直接称为无损 on-policy 训练数据。

## 任务生产与准入成本

三份最终门禁分别用时约 808.1、923.5、848.7 秒，合计约 43.0 分钟。它们包含正反对照和真实环境机制检查，属于任务准入成本，与模型求解成本分开统计。开发前身的门禁另用时约 831.7 秒，没有因其随后被新冻结版本替代而抹去该成本。

新版本测量了控制样本和 Session 的编译、仿真子进程墙钟时间；初始模板和分类探针有部分调用未被计时，因此这些数值只是总门禁时间的子集。三份门禁分别记录约 166 秒的编译调用和 549–660 秒的仿真调用。这些区间包含启动和包装开销，不是纯 EDA 计算时间。原始日志中的仿真 CPU 尾注则合计约 65–68 秒／包，不能将 CPU 秒与墙钟秒混用，也不能未经测量就把差额归因于某个组件。

三条模型试次合计 1,459.3 秒，SDK 记录 194,012 Token（包含单列的缓存读取），其中模型请求墙钟约 75.1 秒、编译调用 830.0 秒、仿真调用 548.0 秒。增强试次用了 132,800 Token、6 次编译；五次编辑与事后首候选检查增加了候选编译成本。编译与仿真时间包含可信终局、保留和事后执行，不能当成纯求解时间，也不能与总墙钟再相加。API 未返回货币费用，保留为 null。

试次启动前的机制检查另约 462.2 秒，增强环境启动检查另约 215.6 秒；独立完整工具验收约 391.5 秒。上述前置成本不包含在模型试次墙钟中，详见[分范围成本记录](../experiments/queue-family-v1/costs.json)。验证器故障探针的用时在其证据中单列；精确私有输入的参考核验另计，不能因复用旧证据而假装又执行了一次仿真。

[源码体积测量](../experiments/queue-family-v1/source-footprint.json)显示每包约 1.08–1.09 MB、251–253 个文件；三包合计 3.26 MB，其中约 55.8% 为相同内容副本。相较此前路由包，主要减少的是研究报告与历史试次副本，不是验证逻辑。这个结果不能证明 EDA 加速，也没有实现跨契约编译缓存。

当前门禁在同一包内把合法参考与错误对照编译为带选择编号的 control bank，随后运行各自测试；报告器重建该编译集合并核对具体编号与源码哈希。这复用了已有合法编译机制，不等于跨任务或跨工具链共享二进制。

生产、静态审查、工业准入与 Rollout 的职责可以复用；地址译码和时间状态的语义检查则仍需各自专用后端。目前保留包内特化与较大的执行源码冻结范围，没有为了节省时间削弱门禁。下一步可以依据测量拆分组件依赖，而不是先建设通用生成平台。

## 可复用范围与研究边界

本轮没有修改原 Task001–004、路由族及历史试次。三个新契约之外的任意深度、不同仲裁、AW/W 不等容量、多目标并发、完整 AXI4 和 PPA 奖励均未开放；也没有进行模型参数训练。

公开 Spec、参考与验证源码可能进入未来预训练数据；求解阶段隔离答案并不证明没有既往数据污染。有限仿真也不是完整功能证明。对于任务难度，应分别查看每个模型、工具条件和任务契约的真实试次，不能把历史不同条件的样本混成一个成功率。

当前最有价值的下一步不是马上生产更多深度组合，而是从第三条的**同一份已确认回归 RTL**出发，匹配 Prompt、输入和预算，比较基础诊断与主动事件查询。预先规定少量配对试次，并观察模型是否定位 RESP 退出条件、验证修复且避免新回归。那才比本轮不同初始候选的一次成败更能研究反馈作用；本轮未额外启动这项实验。

生产架构方面，优先把实际运行源依赖与研究资料分开，并测量前置机制检查能否在完全相同的冻结条件下合法复用。当前已有来源绑定的精确输入证据复用，但没有通用组件缓存或跨契约二进制缓存；这些优化都不得绕过新增契约的真实正反对照。

生成、reset/test/submit、门禁和 Rollout 通过[同一包入口](../task_families/queue_v1/README.md)运行。复跑工业验证需合法 EDA 环境与匹配源码；公开仓库不分发商业工具、完整日志或私有原始向量。
