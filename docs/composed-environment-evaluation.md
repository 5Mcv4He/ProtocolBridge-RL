# 组合任务、验证遗漏与候选回归

把“地址路由”和“请求排队”分别测对，并不意味着两者组合后仍测得充分。本阶段最明确的发现是一次真实漏检：**一个只在目标 2 访问中复位时出错的实现，通过了原组合验证器的全部 25 个 case 和 45 个必要覆盖点。** 同一份 RTL、同一个已编译仿真器，只把已有复位场景的地址移到目标 2，就触发同步复位违例；合法参考在该场景通过。

这个结果说明，组合任务需要验证“哪个目标正在经历哪个生命周期事件”，而不只是分别检查目标切换与复位。它也说明质量门禁只能保证已声明并实际执行的义务，不能把一次准入当成验证器完备性的证明。原始 PASS、后续拒绝和合法参考结果都保留在[同源码证据](../experiments/composed-stage-v1/reset-target-gap/summary.json)中。

本页同时研究第二个问题：工具反馈能否明确说明自己对应哪一份 RTL，并帮助模型修复历史真实回归。工具机制验收和真实模型行为分别报告，不能用前者替代后者。这里没有进行模型参数训练。

## 组合为什么产生新的验证义务

新任务仍采用单个 APB 执行器，但允许 AW、W、AR 各接受两个尚未退休的请求，并将请求路由到三个独立目标。未映射地址产生 DECERR，不访问 APB，却仍占用额度直到 AXI 消费响应。具体合同和系统图见[组合任务说明](composed-task-production.md)。

例如，复位打断目标 0 的访问时，所有输出都能正确清零，并不能说明目标 2 的状态也会清除。此前所有映射复位场景都使用目标 0，目标切换则发生在其他没有复位的场景。两类测试各自存在，交互行为却从未发生。

| 实际对照 | 候选是否变化 | 结果 |
| --- | --- | --- |
| 初版完整 25 case，45 个必要覆盖全部命中 | 条件性目标 2 复位错误 RTL | Reward=1，漏检 |
| 将已有 `reset_5` 移到目标 2 | 同一源码 SHA、复用相同仿真编译产物 | Reward=0，同步复位输出违例 |
| 同一个目标 2 场景 | 合法参考 | Reward=1 |

修订验证器不改变 Spec、初始 RTL 或两种合法参考。它把已有 Setup 复位场景放在目标 1、Access 复位放在目标 2、响应阶段复位保留在目标 0，并增加三个由实际活动复位置位的覆盖点及一个错误对照。验证器修订号为 2，沿用原任务契约号；旧准入结果保存为历史证据，不继承到修订源码。

修订版已完成实际工业准入：两种合法参考均通过完整 25／公开 23 case，19 个功能错误对照全部拒绝，48/48 必要覆盖及 40 项机制与隔离检查通过。每份完整参考的账目为 620 笔计划事务、580 笔检查完成、40 笔复位取消。见[准入摘要](../experiments/composed-stage-v1/composed-v2/summary.json)和[义务—实测证据关联](../experiments/composed-stage-v1/composed-v2/obligation-evidence.json)。

这一安排仍不是完整的“目标 × 所有复位阶段”笛卡尔积覆盖。它检出了已确认的交互缺陷，但更细的阶段依赖错误仍可能遗漏。继续生产更多组合契约时，需要依据风险扩展义务，而不能简单复制这 25 个场景。

## 可信验证环境也会出错

组合开发中，VIP 与 Scoreboard 的连接遗漏曾把合法参考误判为功能错误；复位时未清理 VIP 请求状态又导致验证不可判定。两次使用同一参考源码复验后恢复正确结果，见[连接与复位修正证据](../experiments/composed-stage-v1/verification-corrections.json)。另一个问题是检查器的执行计数只记录复位释放后的周期，因而把复位期间已确认的模板输出违例错归为 null；[相同模板的分类复验](../experiments/composed-stage-v1/reset-liveness-correction.json)保留了修正前后结果。

这些结果不属于模型设计失败。它们说明奖励可靠性既需要错误 RTL 对照，也需要确认可信检查器确实连接、执行，并且自身状态与协议复位一致。

## 怎样判断一个调试工具真正有效

队列任务此前出现过一条真实轨迹：首候选事后通过公开验证，后续编辑却引入 RESP 状态退出延迟，最终失败。本阶段选择该已确认的错误候选作为固定修复起点，比较基础诊断与综合工程工具。两者保持同一 Spec、初始错误源码、模型、动作协议、20 次总动作预算、2 次公开测试及匹配的私有输入；综合条件另允许编译、综合检查、局部实验和事件查询。因此即使结果不同，也只能讨论整个工具配置的探索性差异，不能单独归因于某一个工具。

新增的 `candidate_binding` 在开发反馈中标记当前源码和被测源码的 SHA-256。编辑之后查询旧实验，仍可看到旧行为，但会明确显示它不属于当前候选。这个机制不替模型修复或回退，也不自动给最新版本补测。实际机制与用法见[综合工程环境](engineering-lab.md)。

预检曾因错误对照选择不匹配而拒绝启动模型：一个提前释放额度的实现先被调度检查拒绝，但验收脚本要求容量超限证据。实际终局奖励为 0，功能评分没有误放行。修订环境改用既有、已确认的容量超限对照，并重新冻结验收；这次预检不计为模型试次。[分类及证据](../experiments/composed-stage-v1/preflight-control-correction.json)保留了区别。

## 三条真实试次：反馈曝光不等于修复成功

[预先限定的三条试次](../experiments/composed-stage-v1/study-plan.json)全部运行并通过原始轨迹审计，没有替换失败样本。模型为 `deepseek-flash`、reasoning off，使用同一文本 JSON 原子动作协议；采样沿用 SDK／服务端默认值，不声称确定性。两条修复试次的起始源码、运行源码、模型、协议及私有／保留输入哈希已逐项核对一致。

| 独立条件（每项 n=1） | 有效提交 / 私有 / 保留 | 动作 / 编辑 / 公开测试 | 其他实际工具使用 |
| --- | --- | --- | --- |
| 队列修复，综合环境 | 是 / 0 / 0 | 15 / 3 / 2 | inspect 2、experiment 3、observe 2 |
| 队列修复，基础诊断 | 是 / 0 / 0 | 8 / 3 / 2 | 无 |
| 组合任务，从模板独立求解 | 是 / 0 / 0 | 4 / 1 / 0 | 无 |

[结构化结果](../experiments/composed-stage-v1/study-results.json)保留所有分母、反馈、来源及成本。三条共 27 次动作，动作协议错误为 0；全部有效提交、全部终局 Reward=0，没有 Reward=null 或模型试次基础设施故障。两条修复试次实际得到失败反馈，组合任务试次没有调用测试；其首候选公开失败是事后测量，模型当时并未看到。不能把这三种不同条件合成一个能力成功率，更不能据此推断稳定的工具效果。

所有求解停止后，合法参考又在组合试次使用的精确冻结奖励输入和保留输入上分别完成 25/25 PASS、48/48 必要覆盖，账目均为 620 计划、580 完成、40 复位取消。[输入资格证据](../experiments/composed-stage-v1/analysis/composed-input-qualification.json)仅用于核查评价条件，不回流给模型，也不改变失败提交的奖励。

### 综合环境：看到了过程，仍未建立正确时序

综合试次先收到 `Q_GRANT` 需求诊断，随后三次运行同一个 `address_data` 局部场景，并两次主动查询第 14 周期起的窗口。查询使用数值周期，**没有使用事件索引选择器，也没有自建事务序列**；compile 与 synth_check 均未调用。

第一次编辑仅改变末尾换行，没有修复逻辑。第二次增加 `resp_acked`，却在响应握手后继续保持 VALID，触发新的响应顺序错误。第三次允许在响应退休边沿直接重新选择，实际窗口显示：第 16 周期 APB 完成，第 17 周期 B 握手，同一边沿之后 PSEL 又拉高；独立评分拒绝了没有合法调度的 Setup。见[实际送达窗口](../experiments/composed-stage-v1/repair-combined/observed-final-failure.json)、[最终源码](../experiments/composed-stage-v1/repair-combined/submitted.sv)及[完整工具轨迹](../experiments/composed-stage-v1/repair-combined/exchange/training/rollouts.jsonl)。源码还删除了退休时的计数递减，这是额外的静态风险；仿真在首个错误处停止，没有单独测出它的全部后果。

因此可以确认信息曝光、主动局部查询和相关逻辑修改，不能声称形成了有效修复。真实轨迹中的结果绑定均对应当前源码，没有发生旧结果查询；非当前版本提示的正确性由机制验收证明，本试次不能衡量它是否改善模型行为。

### 基础诊断：回到了已经失败的候选

基础诊断试次首先修改 APB 空闲期输出，但原来的调度失败仍存在。之后它删除 RESP 状态，形成[中间候选 06](../experiments/composed-stage-v1/repair-diagnostic/candidate-06.sv)，又在未测试这版的情况下回退。[最终候选](../experiments/composed-stage-v1/repair-diagnostic/submitted.sv)的 SHA-256 与已在第二次公开测试中失败的候选 04 完全相同。这不是恢复一个已知正确的版本。

[事后测量计划](../experiments/composed-stage-v1/offline-analysis-plan.json)在执行额外仿真前记录了为什么选择中间候选。[实际结果](../experiments/composed-stage-v1/analysis/intermediate-public.json)为公开 **21/21 PASS**，272 笔计划事务中 224 笔检查完成、48 笔复位取消。也就是说，这条轨迹包含公开可通过的中间版本，但模型没有验证它，随后又回到了已失败版本。

这个 PASS 是所有求解停止后的测量，模型当时没有得到；中间候选的私有正确性没有评估。它不替换最终提交，不改变终局 Reward=0，也不能直接当成正确训练答案。它提供的是一个具体研究假设：验证机会的分配、修改后的测试以及候选回退判断，可能比继续增加自然语言诊断更值得单独研究。需要新的匹配试验才能检验这一假设。

### 组合任务：首先失败在继承的调度要求

组合任务试次读取文件、写入一份 RTL 后直接提交，没有使用两次公开测试机会。私有和保留验证均首先发现注册 Setup 延迟：IDLE 边沿只改变状态，下一边沿才驱动 APB 输出，晚于 Spec 规定。见[候选及审计](../experiments/composed-stage-v1/composed-rollout/)。源码还存在两深度数组使用两位无限递增指针、选择时提前释放额度等风险，但当前运行在首个调度错误处停止。

这条记录不能证明新组合能力本身导致失败，因为模型尚未通过继承的基础生命周期要求；也不能测量反馈的修复效果，因为没有任何功能反馈曝光。

### 成本随候选变化，而不只随工具数量变化

| 条件 | SDK Token 总量 | 整条试次 | API 请求耗时 | 编译 / 仿真耗时 |
| --- | --- | --- | --- | --- |
| 综合修复 | 155,130 | 668.4 秒 | 27.0 秒 | 605.5 / 32.6 秒 |
| 基础诊断修复 | 45,380 | 216.9 秒 | 26.5 秒 | 171.0 / 16.5 秒 |
| 组合独立求解 | 14,285 | 122.8 秒 | 23.7 秒 | 83.8 / 13.4 秒 |

合计 214,795 Token，包括 SDK 单列的缓存读取 Token；没有取得实际货币账单。API 请求耗时包含网络和服务开销，不是纯服务器推理时间。整条试次及 EDA 时间包含终局、保留及事后首候选测量，排除工具前置验收与后续补充分析。

综合试次记录到 7 次编译，基础诊断 2 次，组合独立求解 1 次。模型不断修改候选、公开测试与带观测的实验使用不同验证源码时，编译成为主要成本。后文的批量正反对照则只需编译一次、以逐 case 仿真为主。这两个成本来源应分别优化，不能只看任务包文件大小或笼统归因于“工具太多”。

## 生产复用：先测成本，再决定抽象什么

本阶段提取了固定基础源码展开、执行组件测试、依赖清单和来源绑定等通用步骤，任务特有的 Oracle、激励及错误对照仍由生成器负责。没有引入任意契约规则引擎，也没有把历史生成器就地重写。[义务证据核对器](../scripts/obligation_evidence.py)进一步检查来源一致、指定场景确实完成、覆盖确实命中、功能错误对照确实被拒绝；它已用于历史队列和新组合任务。缺少覆盖、场景未执行、结果为 null 或只有编译错误时，不得用它建立功能义务证据。它不授予准入，也不证明场景与覆盖之间的因果归属。

对八份源码包的[字节统计](../experiments/composed-stage-v1/final-source-footprint.json)显示：它们对应七个 Task ID，包含 6,653 个文件条目、31,558,895 字节逻辑内容，按内容哈希去重后为 9,134,112 字节。环境升级包仍是同一个队列任务，因此不能增加任务数量。这个测量说明存在存储复用空间，**不说明相同文件可以互换准入证据或跨工具版本复用二进制**。

两次最终准入的[实际成本](../experiments/composed-stage-v1/admission-costs.json)如下。每份门禁先编译包含合法实现及错误对照的控制库，再按严格匹配的源码输入复用仿真产物；不跨工具链复用历史二进制。

| 已准入源码 | 完整门禁用时 | 正反对照 case 执行数 | 对照阶段编译 / 仿真用时 |
| --- | --- | --- | --- |
| 组合任务，验证器修订 2 | 869.9 秒 | 115 | 85.5 / 522.8 秒 |
| 三深度队列，综合环境源码 | 744.8 秒 | 102 | 89.4 / 415.2 秒 |

完整门禁时间还包括初始模板、机制、隔离及分类探针，不能用表中编译与仿真之和代替。此前被拒绝的开发门禁也产生过[实际执行成本](../experiments/composed-stage-v1/development-control-cost.json)，保留为独立记录。当前测量表明，在这些已复用编译的阶段中，逐 case 仿真调用占主要时间；源码去重不能单独消除这部分成本。这是运行观测，不是跨环境性能基准。

统一[轨迹导出入口](task-rollout-exchange.md)已经用历史路由与队列真实轨迹实际验证。它核对执行来源后调用对应版本的审计器；训练记录、保留评估和离线候选测量分开导出。重新导出同一条轨迹不增加研究样本数。

## 证据和结论的边界

当前结果已经支持两点：组合能力会产生原有义务并集之外的遗漏；候选源码与反馈版本可以由控制器绑定并由离线审计复核。有限仿真不能证明完整功能正确性，工具联用验收也不能证明模型会利用工具定位和修复错误。

[预先声明的试验计划](../experiments/composed-stage-v1/study-plan.json)限定三条模型试次，不按结果追加成功样本。三条试次均有效失败，说明这一小样本没有出现全部成功的饱和现象，但也没有提供终局 0/1 的组间区分；更不能据此判断所有训练算法的价值。轨迹中的相关修改、重复失败和候选回退仍提供行为分析信息。是否适合某个后训练方法，需要更充分的采样及独立训练评估。


## 下一步先研究验证决策，再扩大任务数量

最有价值的近期对照，是固定同一错误起点、模型和工具集合，单独改变公开验证预算或候选比较条件，观察模型能否验证新版本、识别已有失败并避免放弃更好的中间候选。新条件必须重新冻结，不能把本次两个 n=1 条件解释成工具优劣，也不能根据事后 PASS 给模型补写成功轨迹。

任务生产方面，应继续把目标身份与生命周期阶段的交互义务系统化，再扩大实例数量。组合试次首先失败在继承的调度要求，提示难度校准还需要区分基础协议能力与新增组合能力；提供经版本化的部分工程骨架、或选择不同推理条件，都是可以单独测量的方向。当前不宜仅靠增加 Burst、ID 或更深队列来宣称进展。

执行成本方面，值得研究公开回归与带观测实验的可信编译复用，但必须绑定候选、全部验证依赖及工具链，并保持独立终局仿真与权限边界。本阶段只测量并识别了这个瓶颈，没有实现新的跨后端缓存或在线 Rollout Collector。
